# V1 company service catalog migration

Deploy code → read-only fallback protects onboarding → Admin seeds defaults → verify the catalog → dynamic catalog is authoritative → map legacy Company selections.

1. Deploy the code through the controlled release process. When the entire catalog has zero rows, the authenticated onboarding query supplies the original ten services from the same bilingual defaults used by the Admin seed. No query or Company action creates catalog rows. A Company can complete onboarding with stable legacy keys stored in its `companyServices` relationships, ready for later mapping.
2. Open Admin → Service catalog and run **Seed default services**. The empty-catalog warning asks Admin to seed before launch. This inserts the ten defaults by their legacy keys as stable slugs, skips existing slugs, and never overwrites Admin edits. Repeating it creates zero rows and preserves existing IDs.
3. Verify the catalog's ten defaults, FR/EN names, active status, sort order, and custom services. As soon as any catalog row exists, the fallback stops automatically and the database becomes authoritative. Onboarding uses only active catalog rows and saves real service IDs. A catalog containing only inactive rows does not enable the fallback. A fallback form submitted after seeding resolves its legacy keys to the seeded IDs in the mutation.
4. Run **Map existing company selections** after verifying the catalog. It pages through `companyServices` in batches of 50, matches legacy `service` keys to catalog slugs, and patches `serviceId`. Existing relationships and creation timestamps remain. Repeating the migration skips mapped rows; unmatched keys stay untouched and are reported for review. Verify the results, existing profiles, and directory filters. Retain the legacy `service` field during V1.

`serviceId` is the canonical Company reference once a catalog exists. The temporary empty-catalog fallback accepts only the original ten keys, checks Company ownership, and rejects duplicate or unknown values. Catalog seeding remains an explicit Admin action. With a populated catalog, newly added inactive services are rejected, while previously selected inactive services may remain or be removed by the Company. Unmatched legacy rows are preserved. Used slugs cannot be edited; services are deactivated rather than deleted.

Rehearse these steps on development data. This document does not deploy or alter production; any future production rollout must use the controlled release process.

During V1 rollout, `getOnboardingProfile` and `getProfileManager` also retain the original ten legacy keys in `serviceOptions`. Browser sessions running the previous UI can still render their translated options and submit legacy keys. The new UI uses the catalog fields and IDs. Backend validation continues to reject newly selected inactive services. Remove the compatibility response field only in a later cleanup after older browser sessions have been retired.
